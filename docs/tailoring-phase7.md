# Phase 7 — Hardening and acceptance

Phase 7 verifies the complete user workflow and hardens recovery/export boundaries. It adds no automatic generation, application submission, status changes or live-model evaluation.

## Acceptance scenarios

`backend/tests/acceptance_fixtures.py` supplies three fictional cases with different postings, approved records, skills, accomplishments, unsupported requirements and letter prose:

| Role | Selected evidence | Deliberately unmet requirement |
| --- | --- | --- |
| AI | Retrieval with source passages; evaluation on 40 synthetic questions | Production model monitoring |
| Backend | FastAPI idempotency; SQL concurrency/rollback tests | Distributed message queue operations |
| Full-stack | Accessible React/TypeScript forms; API submissions and reload recovery | Native iOS development |

Each case generates a resume through all four stages and three cover-letter variants with different evidence selections. Excluded claims and archived private text never enter provider requests. Backend acceptance uses real persistence, validation, PDF compilation, approval, exports and backup/restore. Only provider responses are mocked. Browser acceptance covers the entire path on desktop and mobile:

1. Paste link and description, extract basics, review a salary concern and NYC eligibility.
2. Continue despite advisory flags; save as **Saved**, without starting generation or detailed analysis.
3. Explicitly generate a resume, review evidence/unmet requirements, mark content reviewed, render, inspect the PDF, approve exact exports and download.
4. Independently generate letters, review all variants, approve the exact saved revision and download.
5. Explicitly run detailed analysis later; preserve the job's status, source description and asset selections, and keep both approved downloads available.

Existing tests also cover Not pursuing, Save for later, duplicate detection, manual fallback, retries, invalid edits, source changes, historical revisions, interrupted generation/checks and artifact cleanup.

## Recovery and export fixes

- Intake source/review drafts, intake retry identities, resume retry identities and description drafts now validate their recovered shapes. Incompatible or malformed content stays downloadable byte-for-byte until explicitly discarded; dependent actions stay disabled. Compatible earlier review drafts remain recoverable, but missing source-review metadata requires a fresh review.
- Recovery controls disclose browser-storage failures. Discarding an incompatible intake in one tab preserves a different draft held by another tab.
- An unsaved recovered description blocks resume generation until saved or discarded. Reloading no longer hides the distinction between unsaved and saved generation inputs.
- Successful intake no longer unconditionally deletes another tab's shared retry identity. Request fingerprints still distinguish a later posting/decision from a retry.
- PDF and letter download clients handle JSON errors, plain-text/HTML proxy failures, network interruptions and empty responses. Retrying uses the saved approved version. Clipboard denial leaves file downloads available.
- Malformed PDF parser failures become validation errors. Unreadable compiler output publishes no artifact and preserves the saved revision/review.
- Lost render responses recover from saved render history; retrying the same revision reuses the artifact. Existing tests retain stale-tab conflict checks, explicit comparison, save/discard isolation, exact approval and historical download protections.

## Compatibility after version changes

Frozen backups were exported by actual historical Git revisions for archive versions **1–7**, rather than generated by current code with an older label. The [fixture manifest](../backend/tests/fixtures/compatibility/manifest.json) records source commits, archive hashes and exact download hashes. The [fixture README](../backend/tests/fixtures/compatibility/README.md) describes their contents and maintenance rules.

Every archive restores into a database created by current Alembic migrations, then re-exports and restores again. Tests preserve generation-v1/v2 history, source exclusions, content-only approvals, final PDF approvals and letter reviews. Model and compiler calls are disabled during restoration and historical downloads. Unknown future archive versions are rejected without replacing current data. Existing tests cover tampered archives, failed commits and pre-restore recovery backups.

Future prompt/schema/validator/layout changes must retain historical verifiers or supply an explicit migration. Do not regenerate these fixtures merely to make a compatibility failure disappear. Version-3 frozen data includes activated sources but no intake decision; current roundtrip tests cover intake review rows.

## Functional evidence versus writing quality

**Phase 7 automated results are mocked functional acceptance.** The letter evidence assessor in these tests is an authored oracle, not an independent demonstration of semantic entailment. Different fixture prose proves correct handling of different inputs and outputs; it does not prove that a live model will choose good evidence or write good letters. Real compilation and exact download checks establish rendering/export behavior only.

No live provider call was made for Phase 7. The earlier [consolidation evaluation](tailoring-consolidation.md) remains historical evidence for the resume pipeline at that checkpoint: its final three samples completed four passes each, and all three polish passes made no changes. It is not a fresh Phase 7 evaluation or evidence of cover-letter writing quality. Live cover-letter quality remains unevaluated.

For a separately authorized live evaluation, keep a separate report under ignored `backend/storage/writing-evaluation/` and record:

- Code commit, generation/validation/prompt versions, model, source-bundle hash, exact posting/options, timestamp, provider attempts, usage and elapsed time.
- Actual AI/backend/full-stack selections and omissions, including deliberately unsupported requirements. Do not use fixture outputs as live expected prose or hide failed attempts.
- Human sentence-level assessment of letter grounding, metric meaning, scope/agency, employer/role attribution and company facts; list unsupported claims explicitly. Model-assessor approval alone is insufficient.
- Readability, specificity to each posting, redundancy, qualification honesty, differences among variants, manual editing required, and whether critique/revision/polish materially helped.
- Functional completion and human writing-quality findings in separate fields. Any invented personal history, ungrounded metric or changed scope is a quality failure even if the workflow completes.

Do not mark evaluation drafts reviewed, approved or applied. This separates optional paid quality evaluation from routine deterministic regression checks.

## Verification commands

Backend: `py -3 -m pytest -q -p no:cacheprovider --show-capture=no --tb=short`.

Frontend: `npm run typecheck`, `npx playwright test`, then `npm run build`. Run browser tests and production builds sequentially because both use `.next`. If the normal frontend test port is occupied, set `UI_FRONTEND_PORT` (PowerShell: `$env:UI_FRONTEND_PORT='3101'`); the fixture's CORS configuration follows that port. The disposable backend remains on port 8100. Existing servers are never reused. Real render tests need the [Phase 5 PDF toolchain](tailoring-phase5.md).

## Acceptance results — 2026-10-22

- **230 backend tests passed**, including real PDF compilation, all seven frozen archives restored through current migrations, exact historical download hashes, unsupported future backups and malformed compiler output.
- **60 browser tests passed** across desktop and mobile, including six distinct-role complete journeys. After the final incompatible-description editing safeguard, its two desktop/mobile cases were rerun separately and both passed.
- TypeScript checking and the production build passed. The build ran after browser servers exited.
- Desktop and mobile PDF-preview screenshots and a desktop letter-review screenshot were inspected. Layout remained readable, controls accessible, and overflow assertions passed; mobile users can open the full-size PDF for detailed inspection.
- **Zero live-model calls.** Provider/semantic-check outputs are fictional fixtures; see the separate quality-evaluation boundary above. User source assets and the production database were not used.

The existing Starlette/httpx deprecation warning remains. An intermediate export test read metadata before approval completed; the test now awaits approval before asserting immutability. Port 3100 became occupied by another local app, so final browser verification used 3101 without stopping or reusing that app. The final full browser run passed without retries.
